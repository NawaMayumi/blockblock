# BlockBlock

赤色の紙・ブロックを検出し、個数と格子状の配置を推定するブラウザプロトタイプです。あわせて、黄色い数字ブロック（答え入力）の認識にも対応しています。静止画（P1）とライブカメラ（P2）の両方に対応しています。

## 使い方

`dist/index.html` を開きます。画面上部の「静止画」「ライブカメラ」タブでモードを切り替えられます。

### 静止画モード（P1）

「写真を選ぶ」またはドラッグ＆ドロップで別の写真を試せます。同梱のサンプル画像（`prototype-red-blocks-sample.png`）は、実物写真の見た目（木目調の背景・赤いブロック・影による区切り）を再現した合成画像です。

### ライブカメラモード（P2）

「カメラを開始」を押すとブラウザのカメラ権限ダイアログが出ます。許可すると、映像上に検出枠・中心点・個数・「段数 × 列数 = □」を重ねて表示します。複数カメラがある端末ではカメラ選択メニューが表示されます。「カメラを停止」でストリームを完全に停止します。

カメラ映像・画像はいずれも端末内でのみ処理し、外部へは送信しません。

**カメラを使うには HTTPS または localhost が必要です。** 普通に `file://` でも Chrome では動くことがありますが、Safari では動作しません。開発中は次のいずれかで配信してください。

```bash
cd dist
python3 -m http.server 8000
# → http://localhost:8000 をMacのChromeで開く
```

iPhone実機など別デバイスから確認する場合は、Mac上の `localhost` はそのままでは届かず、また自己署名証明書のHTTPSはiOS Safariがカメラ利用に必要な「セキュアコンテキスト」と認めないことが多いため、正規のTLS証明書を持つ一時トンネルを使うのが確実です（Homebrewで`cloudflared`/`ngrok`が導入済みならアカウント登録なしですぐ使えます）。

```bash
# 1) dist を配信
cd dist && python3 -m http.server 8000

# 2) 別ターミナルでCloudflareの一時トンネルを起動（アカウント不要）
cloudflared tunnel --url http://localhost:8000
# → 出力される https://xxxx-xxxx-xxxx-xxxx.trycloudflare.com をiPhone Safariで開く
```

`ngrok http 8000` でも同様のHTTPS URLを発行できます。いずれも一時的な公開URLなので、確認が終わったらプロセスを停止してください（誰でもURLを知っていればアクセスできる状態になります）。

## 実物ブロックの仕様（2026-09-07 改訂）

実機写真をもとに、検出対象を全面的に作り直しました。

- **掛け算ブロック**：赤〜マゼンタ系の紙で包まれた正方形の立体。各面は「やや明るいピンクの縁」と「中央のやや暗いワインレッドの正方形」の二層構造ですが、どちらも同じ赤系の色相なので、検出上は面全体を「赤」として扱います。
- **ブロック同士の区切り**：白い余白ではなく、隣接ブロックの間にできる**影の切れ目**で区切られる設計です。検出側は、赤マスクの行・列方向の密度を見て、影で密度が下がる位置をピーク検出することで格子を分離します（`detectTouchingGrid`。ロジック自体はP1から流用し、色の判定だけ赤用に置き換えています）。
- **背景**：白〜薄いグレーの無地ではなく、木目調の机を想定しています。色判定は色相ベース（R・G・Bの比率）にして、オレンジ系の木目と赤/マゼンタのブロックを区別するようにしました。
- **答えの数字ブロック**：黄色い紙で包まれた立方体で、**どの面にも**「黒い正方形のシール＋白いFutura Boldの数字」が付いています。以前検討していた「向きを判定するための小さなグレーの目印」は今回の写真にはなく、**回転補正マークなしで実装**しています（後述のリスク参照）。

## 検出ロジックの変更点

- `greenPixel` を `redPixel` に置き換えました。R−Gの差とG−Bの差の両方を「赤らしさ」スライダーでスケールし、木目（オレンジ系、B≪G）と赤ブロック（B≈G以上）を区別します。
- `components()` / `detectTouchingGrid()` 内部の `green` フィールドは、色に依存しない `matched`（対象色として判定されたピクセル数）に名称変更しました。
- `detectTouchingGrid` の密度ピーク検出のしきい値を、白枠のときより緩め（`maxValue * .30` → `.22`）にしています。影による密度の谷は、白枠ほどはっきり出ない可能性があるための調整です。
- 数字ブロックの検出（`detectAnswerCards`）: 黒い正方形シールを連結成分として抽出するロジックはそのまま維持しつつ、**周囲に黄色があるかを確認する `hasYellowSurround()` を追加**しました。これにより、シール以外の黒い物体（影・他の小物）を答えとして誤認しにくくしています。
- 数字のデコード（`decodeDigitCard`）: 当初は「向きが分からないので0°/90°/180°/270°すべてを試して一番自信度が高いものを採用する」実装にしていましたが、**テストで「6」を「9」と誤読するケースが見つかりました**（Futura Boldの6を180°回転させると9として非常に高い confidence でマッチしてしまうため）。実物は「常に正しい向きで置く」前提なので、あえて回転探索をやめ、**0°のみでデコードする**方式に変更しています。詳細はコード中のコメント（`decodeDigitCard`）を参照してください。
- 「答えエリア」のデフォルト位置（`CARD_ZONE`）を、画面下部の帯から**画面左側の縦長エリア**に変更しました。ただし後述の実機テストで「置き場所は写真と違う場所（右側）でもよい」ことが分かったため、**「答えエリアだけを見る」は既定でOFF（全画面走査）**にしています。置き場所を毎回固定できる場合のみONにしてください。
- `redStrength` スライダーの初期値は25（0〜45の範囲）にしています。

## iPhone実機テストで見つかった不具合と修正（2026-09-07）

実機（iPhone Safari）で試していただいたところ、2つの重大な不具合が見つかり、修正しました。

1. **カメラを離すとブロック12個が「1個」になる**：影の切れ目でブロックを分離する処理（`detectTouchingGrid`）が、影の谷を検出する際の「なめらかにする範囲（スムージング半径）」を**画面全体のサイズ**を基準に計算していました。ブロックが遠くて画面上で小さくなると、実際の影の隙間（数ピクセル）よりスムージング範囲の方が大きくなり、隙間ごと均されて消えてしまうため、12個のかたまりがまるごと1個の塊として扱われていました。
   - 修正：まず赤い領域のかたまり（連結成分）を見つけ、**そのかたまり自身の大きさを基準に**スムージング範囲を計算し直すようにしました（`runDetection`が各かたまりに対して個別に`detectTouchingGrid`を実行）。これにより、近距離〜かなり遠距離（ブロック1つが数十pxしかない場合）まで正しく分割できることを確認しています。
   - あわせて、1行または1列だけが接触しているような並び（例：1×3）も正しく分割できるよう`detectTouchingGrid`を拡張しました。ただし、格子として式を表示するには最低4個以上のブロックが必要という既存の制約はそのままです（3個以下では個数のみ表示、式は出ません）。
2. **数字ブロックが全く検出されない**：「答えエリアだけを見る」が既定でONになっており、かつそのエリアを実物写真をもとに画面左側に固定していたため、実際に右側に置かれた数字ブロックが最初から検出範囲の外でした。
   - 修正：上記の通り、既定を「画面全体を見る」に変更しました。無関係な黒い物体の誤検出は`hasYellowSurround()`（黄色に囲まれているかの確認）で別途防いでいるため、エリア限定は必須ではありません。

これらはPlaywrightでの自動テストでは再現できなかった不具合です（合成テストでは常に十分な大きさ・十分なコントラストの画像を使っていたため）。実機でのテストがなければ見つけられませんでした。

## 2回目の実機テストで見つかった不具合と修正（2026-09-07 続報）

1. **数字ブロックが全く検出されない（依然として）**：写真を見ると、手の影が画面のかなりの面積を占めていました。黒いシールを判定するしきい値（`cardContrastThreshold`）は**画面全体（または答えエリア全体）の明るさの分布**から1つだけ計算していたため、大きな影がその推定を狂わせ、影自体が「黒いシール候補」として誤検出され（写真に写っていた謎の枠がこれです）、逆に本物のシールは正しく判定されていませんでした。
   - 修正：画面を約140px四方のタイルに分割し、**タイルごとに**しきい値を計算し直す「局所適応しきい値」（`buildLocalDarkMask`）に変更しました。合成テストで、画面の半分を覆う濃い影がある状態でも、影から離れた場所にある数字ブロックを正しく検出できることを確認しています（影そのものからの誤検出もなし）。
   - あわせて、実機カメラでの黄色の見え方は写真より彩度が低く出る可能性を考慮し、黄色判定のしきい値も少し緩めました。
2. **赤ブロックが実際より1列多く数えられることがある**：影の谷を検出する方式は、カメラのノイズ（圧縮ノイズ・モアレなど）で偶発的に生じる小さな密度の谷を、本物の区切りと誤認することがあります。ピーク間の最小距離・高さのしきい値を少し厳しめに調整しましたが、根本的な解決には**各面の中央に白い印（テープなど）を付けていただく**方式への切り替えをおすすめします。印を付けていただければ、白い正方形を検出する方式（最初の緑ブロック版と同じ、実績のある方式）に切り替えます。

**デバッグ表示を追加**：「こたえブロック設定」内の「デバッグ表示」チェックボックスをONにすると、ライブ映像に判定結果を色分けして重ねて表示します（緑＝赤ブロックと判定／オレンジ＝黄色と判定／青＝黒いシール候補と判定）。実機での色の見え方は写真だけでは正確に分からないため、今後もし正しく検出できない場合は、このデバッグ表示のスクリーンショットを送っていただけると、憶測ではなく実際のデータを見て調整できます。

## 黄色い印（テープ）モードを追加（2026-09-07 続報2）

実際に黄色いテープを各面の中央に貼ったブロックの写真をいただいたので、それを検出する方式を実装しました。

- 「検出調整」内に**「黄色い印（テープ）を使う」**チェックボックスを追加しました（既定OFF＝これまで通りの影ベース判定）。ONにすると、影の谷を探す方式（`detectTouchingGrid`）を使わず、代わりに**赤に囲まれた黄色い小さな四角**を1個ずつ検出する方式（`detectMarkedBlocks`）に切り替わります。
- 印は数字ブロックの黄色い紙と同じ色判定（`yellowPixel`）を再利用しています。マーカー同士は隣接ブロックが接触していても互いに触れ合わないため（間に必ず赤い余白がある）、影の検出をまったく必要とせず、単純な連結成分検出だけで済みます。理論上、距離に関係なく安定するはずです。
- 合成テストで、印付きの3×4配置を近距離〜ごく遠距離（ブロック1個34px相当）まで検証し、いずれも confidence 1.0 で正確に「12個・4×3」を検出できることを確認しました。
- ONにする場合は、**すべてのブロックに印が必要**です（印のないブロックは検出されません）。まだ一部のブロックにしか貼っていない場合はOFFのままにしてください。
- 既存の影ベース判定（OFF時の挙動）には変更を加えていないため、印をまだ貼っていない場合の動作は今まで通りです。

## カメラのライト（トーチ）自動ON（2026-09-07 続報3）

影ができにくくするため、カメラ開始時に端末のライトを自動でONにするようにしました（`MediaStreamTrack.applyConstraints({advanced:[{torch:true}]})`）。手動での切り替えUIは不要で、対応環境では自動で点灯します。

**重要：iPhoneのSafariはこの機能に対応していません。** これはWebアプリ側の実装の問題ではなく、iOS SafariがWeb標準の`torch`制約そのものを実装していないためです（AndroidのChromeでは動作します）。この制限はページ側のコードでは回避できません。

- 対応している場合はカメラ開始ボタンの隣に「ライト ON」、非対応の場合は「ライト非対応」と表示されます（iPhoneでは常に「ライト非対応」と出るのが正常な挙動です）。
- iPhoneで影を減らしたい場合の代替案：
  - 部屋の照明を明るくする、または別の光源（デスクライトなど）を斜め上から当てて、影が薄く広がるようにする。
  - スマホのカメラ位置をできるだけ真上（ブロックの真上）に近づけると、スマホ自体の影が画角に入りにくくなります。
  - 「黄色い印（テープ）モード」をONにしていれば、そもそも影の有無に判定が左右されなくなるため、この問題自体の影響を受けにくくなります。

## 格子認識をやや雑な配置にも対応（2026-09-07 続報4）

黄色い印モードは全距離でconfidence 1.0という良い結果でしたが、「少し雑に並べると個数だけになり式が出ない」という声をいただきました。原因は、行・列としてまとめる際の許容範囲（クラスタリングの許容誤差）を**印（テープ）自体の大きさ**から計算していたことです。印はブロック本体よりずっと小さいため、実際のブロックの間隔に対してこの許容範囲が過剰に厳しくなっていました。

行・列のまとめ方を、位置を並べたときの「隙間の自然な区切り」を見つける方式（`clusterAdaptive`）に変更しました。ブロック本体の大きさに依存せず、実際の配置の間隔から自動的に適切な許容範囲を判断します。合成テストでは、配置間隔の最大20%程度のズレ（かなり雑な置き方）でも正しく段数×列数を認識できることを確認しました（30%以上ズレると、さすがに個数のみの表示に留まります＝行と列の判別が本当に怪しくなるラインです）。

## 数字ブロックの検出方式を根本から見直し（2026-09-07 続報5）

これまで3回、数字ブロックの検出改善を試みて、いずれも実機では不十分でした（ROIの位置ずれ→修正、影による全体しきい値の破綻→局所適応しきい値で修正、それでも遠距離では全く検出されない、という経緯）。今回、**なぜ遠距離でだけ失敗し続けたのか**を検出の「順序」に着目して考え直しました。

**反省点**：これまでの実装は「まず黒いシールを探し、その周囲に黄色があるか（`hasYellowSurround`）を確認する」という順序でした。この「周囲の黄色の輪」は、シール本体に比べてかなり薄い帯（数〜十数px程度）です。実際のカメラ映像では、光学的なボケ・センサーノイズ・動画圧縮によって、**細い帯状の色特徴から先に潰れていきます**。これは静止画をどれだけ目視確認しても気づけない種類の劣化で、実機の遠距離テストで初めて表面化しました。一方、赤ブロック検出や黄色マーカー検出が距離を問わず安定していたのは、どちらも「面全体」という大きな領域だけを見ていたからです。つまり、数字ブロックの検出ロジックだけが、他の検出方式と違う「细い特徴に依存する」設計になっていたのが、根本原因でした。

**修正**：検出の順序を逆にしました。
1. まず黄色い面全体（大きな領域）を、赤ブロックの検出と全く同じ考え方で先に見つける（`components`の再利用）。
2. 見つかった黄色い面の**内側だけ**を対象に、黒いシールを探す（局所適応しきい値`buildLocalDarkMask`はそのまま再利用）。

これにより、数字ブロックの検出も「大きな領域から先に見つける」という、他の検出方式とまったく同じ、距離に強い設計になりました。`hasYellowSurround`は不要になったため削除しています。

合成テスト（木目調の背景、3個の数字ブロックを220px〜18pxまで5段階の大きさで検証）では、**どのサイズでも3個とも検出に成功**し、confidenceはサイズに応じてなだらかに下がるだけでした（220pxで56〜63%、18pxでも22〜41%）。以前のように「一定サイズを下回ると突然ゼロになる」という壊れ方はなくなりました。極端に小さい場合の誤読は35%未満のconfidenceに収まるため、既存の確定しきい値でそのまま安全側に倒れます。

なお、この修正作業の途中で別の回帰も見つかりました：黄色判定を絶対的な色差（`r - b > 閾値`など）で行っていたため、明るい木目調の背景（赤ブロックのサンプル画像と同じ色）が「黄色」として誤判定され、黄色いキューブ全体が背景と融合してしまう問題です。判定をR/B・G/Bの**比率**ベースに変更し、この回帰も解消しました。

## 解像度・オートフォーカスの調整（2026-09-07 続報6）

実機で数字ブロックが「一瞬だけ検出される」（片方の数字は高いconfidenceで読めるのに、両方同時には安定しない）という報告があり、ピント（フォーカス）の甘さが疑われました。以下を追加しました。

- **カメラの要求解像度を明示的に引き上げ**：以前は解像度を指定しておらず、端末が控えめな解像度を選んでいた可能性があります。`width/height`を4K相当（ideal）で要求するようにしました。解析自体は引き続き最大1100px幅に縮小して行うため処理負荷は変わりませんが、縮小前の元映像がより高精細になることで、特に小さく写る数字シールのディテールが残りやすくなることを期待しています。
- **オートフォーカスの明示的な有効化（対応環境のみ）**：ライトのON/OFFと同じ仕組み（`MediaStreamTrack.applyConstraints`）で、`focusMode: 'continuous'`を対応時に自動適用します。**この機能への対応状況はブラウザ・端末依存で不確実です**（Androidの一部Chromeでは動作しますが、iOS Safariでの対応は未確認です）。ちなみに前回「iPhoneのSafariはtorch（ライト）に非対応」とお伝えしましたが、実機のスクリーンショットで「ライト ON」の表示を確認しました。より新しいiOS/Safariでは対応が進んでいる可能性があり、訂正します。フォーカスも同様に、実際に効くかどうかは試していただくまで分かりません。

**それでも改善しない場合に試していただきたいこと**：
- スマホを手持ちではなく、何かに立てかけるなどして完全に固定する（手ブレはピントのブレより大きく画質に影響することが多いです）。
- カメラの選択メニューで「Back Triple Camera」のような複数レンズをまとめた仮想カメラではなく、単一のレンズ（例：メインカメラのみ）が選べる場合はそちらを試す（複数レンズを自動切り替えする仮想カメラは、境界的なズーム倍率でピントが不安定になることがあります）。
- スマホのカメラには最短合焦距離（多くの機種で10〜15cm程度）があります。数字ブロックにスマホを近づけすぎている場合、それより少し離してみてください。

## テスト状況

- Node の構文チェック（`node --check dist/app.js`）を実施済み。
- Playwright（Chromium）で以下を自動テスト済み：
  - 静止画モードでのブロック検出（同梱の合成サンプル画像で「3 × 3 = 9」を検出。カメラモードへの往復後も含む）。
  - モード切り替え時のUI表示、フェイクカメラでの起動/停止/トラック解放、4種のカメラエラーメッセージ、`OverconstrainedError`時のフォールバック（いずれも回帰なし）。
  - ブロック側の時間安定化ロジック（2秒確定・調整中表示・保持切れ後リセット・10秒間のノイズ耐性）。
  - **数字ブロックの合成テスト**：黄色い立方体＋黒いシール＋白いFutura数字（5・6・9）を模した画像で、3つとも正しい数字を検出。周囲に黄色がない裸の黒い正方形は答えとして検出されないことを確認。
  - 数字ブロック側の時間安定化・`airwritingresult`イベント発火（確定・単発ノイズでの保持・除去後リセット・新しい答えでの再確定）にも回帰なし。
  - **距離のバリエーション**：同じ3×4配置を、ブロック1個が220px相当（近距離）〜34px相当・隙間1px（かなり遠距離）まで6段階の大きさで検証し、いずれも正しく「12個・3×4」を検出。
  - **分離パターン**：孤立した単独ブロック（式なし・個数のみ）、大きく離れた2×3配置、離れた場所にある2つの別クラスタ（2×2と1×3）が混在するケース、を検証。それぞれ期待通りの挙動（個別クラスタは正しく分割されるが、無理に1つの格子として式にはしない）を確認。
- **重要な注意**：色のしきい値（`redPixel`/`yellowPixel`の定数）は、共有していただいた実物写真を**目視で観察して**設計した値であり、実際のカメラ映像からピクセル値を測定して較正したものではありません。木目の色味・照明・カメラの色再現によって実機では正しく動作しない可能性が十分にあります。「赤らしさ」「ブロックのコントラスト補正」スライダーで実機調整することを前提とした実装です。

## 解像度を下げ、数字の判定ロジックを見直し（2026-09-07 続報7）

実機テストで「①4K解像度要求が重すぎる」「②黄色・黒の検出はできているようだが、数字の判定（0〜9のどれかを当てる部分）が不安定」という2点のフィードバックをいただきました。

1. **解像度を1280×720（ideal）に引き下げ**：4K相当は映像デコードの負荷が大きく、常時デコードし続けるライブカメラ用途には過大でした。720pは実写映像処理でよく使われる軽量な設定です。Chromebookなど4K非対応カメラでも`ideal`指定なのでエラーにはならず、そのカメラの上限にフォールバックします。
2. **数字判定（テンプレート照合）をより柔軟に**：`digit-model.js`の照合方式を、ピクセル単位の完全一致に近い方式から、**数ピクセルのズレ・太さの違いを許容する方式**（各テンプレートを1px分だけ膨張させた上で重なりを見る、簡易的なchamfer distanceのような手法）に変更しました。あわせて、テンプレートに±6度の回転バリエーションを追加し、多少傾いて置かれた場合にも対応しやすくしています。
   - **注意**：この変更の直後、確信度（confidence）が全体的に下がりすぎる問題が一度発生しました（許容範囲を広げたことで「どの数字にもそこそこ似ている」状態になり、正解と不正解の差が縮まったため）。confidenceの計算式の鋭さ（softmaxの温度に相当するパラメータ）を再調整し、はっきりした画像では高いconfidence（90%超）に戻ることを確認しています。
   - 合成テストでは、この変更後も「6」と「9」の区別は引き続き正しく機能することを確認しました。
- この変更は**実際のカメラのボケ・ノイズに対する耐性を上げることを狙ったもの**ですが、合成テスト（完全にクリーンな画像）ではその効果を直接は測れません。実機でどこまで改善するかは試していただく必要があります。

## タップして数値を確認できる診断機能を追加（2026-09-07 続報8）

## Futuraフォントの実機での有無を確認する仕組みを追加（2026-09-07 続報11）

数字判定の精度について「既存のOCRソフトを使っているのか、Futuraのベクターデータで似ているか判定した方がよいのでは」というご質問をいただきました。訂正と対応は以下の通りです。

- **訂正**：既存のOCRソフトは使っていません。`digit-model.js`は、ブラウザのCanvas APIで実際に`Futura`フォントを描画してテンプレートを作っており（`ctx.font = '700 72px Futura'`）、これは既にFuturaの本物のベクター（アウトライン）データをブラウザの描画エンジンで直接ラスタライズしている状態です。カメラ側の入力はどうしても写真＝ラスター画像なので、比較そのものをベクター空間で行うメリットは限定的です。
- **より疑わしい原因に気づきました**：このテンプレート生成は、**カメラが動いている実機（iPhone/Chromebook）のブラウザにインストールされているフォント**に依存します。もし実機に`Futura`が入っていなければ、`ctx.font`は黙って別の書体にフォールバックし、テンプレート自体が最初から違う形になります。これはどんなマッチング精度の改善でも直せない根本的な問題です。
- **診断機能を追加**：ページ読み込み時に、実際に使われているフォントが指定した`Futura`と一致しているかを自動チェックする仕組み（`isFontAvailable`、幅の違いを比較する古典的な手法）を追加しました。一致していない場合、「こたえ（数字ブロック）」パネルに警告（⚠️ Futuraフォントが見つかりません）が自動表示されます。Mac（このテスト環境）ではFuturaが標準搭載されており警告は出ませんでしたが、**iPhoneやChromebookでも同様に警告が出ないか確認していただけますか**。
- **もし警告が出た場合**：実際にプリントされた数字シールに使われているFuturaのフォントファイル（.otf/.ttf）を共有していただければ、`@font-face`でページに直接埋め込み、端末のフォント有無に関わらず必ず正しい書体でテンプレートを生成できるようにします。ただしFuturaは商用フォントのため、Web埋め込みの利用許諾がお使いのライセンスに含まれているかはご確認ください（デスクトップ用ライセンスはWeb埋め込みをカバーしないことが一般的です）。

## タッチさせた数字ブロックの検出・確定までの粘り強さを改善（2026-09-07 続報13）

SVGテンプレート化により、離して置いた数字ブロック単体では高いconfidence（実機で97%等）が出るようになりましたが、実機で新たに2つの問題が見つかりました。

1. **数字ブロックをくっつけると検出されなくなる**：`detectAnswerCards`は「赤いかたまり1つにつき、一番大きい黒シール1個だけ」を取り出す設計でした。2桁の答え（例:「61」）を作るためにブロックをくっつけると、赤いかたまりが1つに融合し、シールも2つ存在するのに1個しか取り出せていませんでした。
   - 修正：赤いかたまりの中にある**条件を満たす黒シールを全て**取り出す方式に変更しました。あわせて、かたまりの縦横比・面積の許容範囲を、2〜3個のブロックが融合した場合も通るように緩めています。合成テストで、2桁・3桁とも隙間なくくっつけた状態で、離して置いた場合と同じ精度で全ての数字を検出できることを確認しました。
2. **confidence 97%でも表示が点滅する**：原因はconfidenceのしきい値ではなく、**フレームごとの検出自体**が（ブロックが静止していても）時々途切れることでした。安定確定の判定窓を1.05秒→2.2秒に、必要な一致率を62.5%→40%に、保持時間を1.6秒→2秒に、それぞれ緩めました。合成テスト（検出が約55%の頻度でしか成功しないという厳しい断続状況を再現）で、以前なら確定できなかったであろう条件でも正しく確定でき、かつブロックを完全に取り除いた場合は最終的に（若干遅れて、4〜5秒程度）未確定表示に戻ることを確認しています。
   - **トレードオフ**：確定しやすくした分、ブロックを取り除いてから表示が消えるまでの時間が以前（約2.6秒）より長くなっています（最大4〜5秒程度）。実機で試してみて、この待ち時間が気になるようであれば調整します。

## 残っているリスク・既知の制約

- **色のしきい値は実機未較正**：上述の通り、`redPixel`/`yellowPixel`の閾値は写真の目視観察による初期値です。実際のカメラ・照明・木目の色味に応じて、スライダーでの再調整がほぼ確実に必要です。
- **影による区切りの信頼性**：ブロック同士が完全に密着し、影がほとんど出ない置き方をされると、`detectTouchingGrid`の密度ピークが検出できず、グリッドが正しく分離できない可能性があります。実機でブロックの間隔・照明条件を見ながら`detectTouchingGrid`のパラメータ（ピークしきい値・最小距離など）の再調整が必要になる場合があります。
- **1×2・1×3など「4個未満」の並びは式が出ない**：`inferGrid`は誤って偶然の並びを式に変換しないよう、最低4個のブロックがないと段数×列数の判定を試みません。3個以下は個数（例:「3個」）だけが表示され、「1×3=□」のような式にはなりません。これは今回の修正以前からの既存の仕様です。1×2・1×3のような掛け算も式として出したい場合は、この閾値の見直しが必要です。
- **数字ブロックの6/9問題**：回転補正マークがないため、数字ブロックが誤って上下逆に置かれると、「6」は「9」として（confidenceも高いまま）誤読される可能性があります。これは実装のバグではなく、目印なし設計に内在する制約です。運用上は「必ず正しい向きで置く」ことを徹底いただくか、将来的に小さな向き判定マークを復活させることをご検討ください。
- **信頼度スコアの閾値（`GRID_CONFIDENCE_THRESHOLD = 0.45`）は暫定値**です。実際のカメラ映像（手ブレ・照明ムラあり）での適合度は未検証です。
- **facingMode指定はデバイス依存**：一部のノートPC/Chromebookでは背面・前面の区別がなく、`ideal`指定が無視されることがあります。
- **iPhone実機でのHTTPS配信手順は開発補助用**（自己署名証明書やトンネリング）であり、本番運用には正式なHTTPS配信が別途必要です。
- 教師向けカリキュラム編集機能、ユーザー登録・クラウド保存、ARKit等の3D空間認識は今回のスコープ外です。

## たし算・ひき算モードの追加（2026-09-08 続報19）

優先順位のご相談を受け、たし算・ひき算モードを実装しました。物理的な意味づけは「画面中央に＋（またはー）の記号、左右に枠を用意し、それぞれの枠内のブロックを数える」というご提案いただいた方式です。新しい物理教材（新しい色のブロックなど）は不要で、既存の黄色マーカー付き赤ブロックをそのまま使います。

- ＋／−モードでは、掛け算の「行×列のグリッド判定」の代わりに、既存の黄色マーカー個別検出（`detectMarkedBlocks`。グリッド構造を前提としないので、バラバラに置かれたブロックでもそれぞれ独立に検出できます）を流用し、左右それぞれの枠内にあるマーカーの数を数えます。
- 表示は「4 + 3 = ?」「4 − 3 = ?」のように、**両方のオペランド（左右の個数）は表示しつつ、答え（合計・差）は一切表示しません**。掛け算の「行×列は見せるが積は見せない」という設計をそのまま踏襲しています。

- 静止画テストモード（🖼️、アルゴリズム確認用）は従来通り掛け算のみ対応です（この機能は検出精度確認用のツールであり、ゲームの一部ではないため）。
- テスト：Playwrightで、(1) 「detectMarkedBlocks」をスタブして左右の個数を自由に制御し、たし算・ひき算それぞれの数式表示が正しいこと・答えがどこにも表示されないこと、(2) 引き算で正しい答えのカードを置いた時だけ正解演出が発火すること（たし算の答えと引き算の答えを混同していないこと）、(3) 片方の枠が空の時に「0が答え」のように誤解釈されず「両方の枠にブロックを置いてください」と表示されること、を確認しました。カメラで実際に２つの枠とその間の記号が描画されることもスクリーンショットで確認済みです。既存の掛け算の回帰テストも全て問題なしです。

## 検出精度の細かい調整4件（2026-09-08 続報23）

1. **数字ブロックのシールの縦横比を狭めた**：カメラは真上から数字ブロックの面を撮るため基本的に正方形のはずなのに、判定コードは1:2に近い縦横比まで許容していました（`.5〜2`）。これを`.65〜1.55`に狭め、明らかに正方形でない候補を早い段階で除外するようにしました。実際のカメラ角度・レンズ歪みで多少ズレる分の余裕は残しつつ、極端な縦横比は弾くようにしています。
2. **1×3のような一列の並びが式として表示されない不具合を修正**：原因を調べたところ、これは掛け算ブロックを個々のブロックに分離する処理（`detectTouchingGrid`）の問題ではなく、その後段の「グリッドとして解釈する」処理（`inferGrid`）内で使っている「値の集まりを自動でグループ分けする」アルゴリズム（`clusterAdaptive`）が、**等間隔に並んだ値をうまく分割できない**という特性を持っていたことが根本原因でした（グループ分けは「密集と密集の間に明らかに大きな隙間がある」ことを手がかりにする方式なので、隙間が全部同じ間隔だと「分割すべき境目がない」と判断してしまいます — これは2次元グリッドでは同じ列が複数行に渡って繰り返されるため問題になりませんが、1行だけの並びではその繰り返しが無いため表面化していました）。1行・1列のケースを直接判定する専用の処理を追加して対応しました。2×3や3×4など、複数行複数列のグリッド判定のロジック自体は変更していません。
3. **「2×3=」の前にある謎の棒線（–）を削除**：以前、HUDの表示からブロック総数の表示を取り除いた際、表示欄そのものの初期値（HTML上のデフォルト値）を消し忘れていたのが原因でした。カメラを一度も停止せずに使い始めた最初のセッションでのみ表示されてしまっていました。
4. **同じ組み合わせの再カウント条件を「6秒経過」から「赤ブロックの形が変わるまで」に変更**：前回入れたクールダウン方式（6秒間は同じ組み合わせを再カウントしない）を、ご要望通りシンプルな条件に置き換えました。今は「実際に検出されている赤ブロックの確定した配置（掛け算のグリッド、たし算の2ゾーン、ひき算の山）が、前回せいかいした時から変化した」時だけ再カウントを許可します。数字カードだけを入れ替えても（例：正解→わざと不正解→また正解、ブロックはそのまま）再カウントされません。ページの再読み込みでも当然リセットされます。
   - この判定には、既にある「安定化（stabilizer）」の確定値をそのまま使っているため、フレームの瞬断による誤カウントの再発はありません。

- テスト：`inferGrid`の1×N/N×1判定を直接呼び出す単体テストを新規追加（単独ブロック→null、2〜3個の一列→正しく認識、斜めの2個→null、近すぎる重複検出→null、を確認）。既存の全回帰テスト（21本）もすべて問題なしです。

「answer block」より「number block」の方が分かりやすいというご指摘に沿って、画面上に表示される文言・見出しをすべて「Number」に統一しました（HUDの「Answer」ラベル、設定ドロワーの見出し「Answer block settings」、スイッチの説明文、チュートリアル本文、開始前の案内文、カメラ映像に直接描画される「Answer」ラベル3箇所など）。内部のコード上の変数名・関数名（`answerZone`や`detectAnswerCards`など、画面には表示されない実装上の名前）は、外部連携用に公開しているAPI（`window.AnswerCards`など）との整合を保つため、あえて変更していません。

### チュートリアルの絵を実物に忠実な自作グラフィックに変更

「赤→黒の絵文字だと、ブロック自体の色が変わるように見えて紛らわしい。そもそも赤い点々の枠のはず」というご指摘の通りでした。実物は「数える用のブロック（赤い本体＋黄色い印）」と「数字ブロック（赤い本体＋黒いシール＋白い数字）」のどちらも**本体は赤色のまま**で、違いは中の印だけです。絵文字ではこの違いを正確に表現できないため、この2つを実物同様に描いたSVGグラフィックを自作し、チュートリアルの該当ステップに差し替えました。

### 宝石アニメーションが得点表示に届く前に消えてしまう問題を修正

これまでは「宝石が得点表示まで飛んでいく動き」と「宝石が透明になって消える動き」が同じタイミング（飛行の100%地点）でちょうど終わるように作っていたため、見た目としては「得点表示にたどり着く直前に、まだ移動中のまま消えてしまう」ように見えていました。位置の移動を飛行の72%の時点で先に完了させ、残りの28%は「すでに得点表示の場所に到着した状態で、その場で縮みながらフェードアウトする」という2段階の動きに変更しました。これにより、宝石が実際に得点表示まで**目に見えて到達してから**消えるようになりました。

### 得点が増えるタイミングを宝石の到着に同期

以前は「せいかい」と判定された瞬間に即座に得点の数字が増えていたため、宝石がまだ画面を飛んでいる途中なのに数字だけ先に増えてしまい、不自然でした。得点を実際に加算する処理を、宝石が上記の「到着」地点に達したタイミングまで遅らせるように変更しました。この判定は3D描画（Three.js）の関数の外に独立した処理として実装したため、万が一WebGLが使えず宝石の3D演出自体が表示されない環境でも、得点の加算タイミングは変わらず正しく動作します。

- テスト：宝石の飛行・得点加算タイミングをテストする`test_gem_flight.js`を新しいタイミング仕様に合わせて全面的に書き直し、「到着前は加算されない」「到着の瞬間に1回だけ加算される」「3D描画だけでは加算されない（得点加算とThree.jsの描画が独立している）」の3点を明示的に確認するようにしました。また、設定ドロワーに移動した停止ボタンをドロワーを開かずにクリックしようとしていた`test_app.js`の既存の不具合（今回の変更とは無関係の、以前からの見落とし）も合わせて修正しました。既存の全回帰テスト（21本）はすべて成功しています。
